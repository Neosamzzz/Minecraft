# 项目目录与生成文件规范

本规范适用于当前 Minecraft 仓库及后续加入的模块。目录按职责划分；只在实际使用时创建，不预建空目录。

新增内容先放入职责匹配的已有文件和目录，只有需要独立维护时才拆分。重复或被替代的内容应合并、删除并更新引用，不保留仅作跳转的空壳，也不默认新建归档目录；历史版本由 Git 查询。测试脚本仅保留可复用的检查，日志、截图、解析结果等输出放入下述固定检查目录，不随每次测试新建文件夹或提交一份报告。

## 目录职责

| 位置 | 内容 | Git |
| --- | --- | --- |
| 各模块目录 | 源码、资源、模块构建配置与专项测试脚本 | 提交必要文件 |
| `tools/` | 跨模块或共用的构建、检查入口及其测试 | 提交 |
| `dev-tools/` | 构建必需、不能直接由当前源码生成的固定材料 | 必需材料与说明提交 |
| `build/libs/` | 统一交付的最终模组包，可保留多个明确版本 | 不提交 |
| `build/checks/<模块>/<检查项>/` | 专项检查产生的日志、编译类和临时配置 | 不提交 |
| `.local/` | 本机测试环境、依赖路径配置及辅助资料 | 不提交 |
| `server/` | 本机运行实例、管理入口与自动备份 | 不提交 |

各模块的 Gradle 中间产物仍由原构建系统管理，保留在模块自身 `build/` 中；系统临时目录中的短期测试数据在测试结束后清理。不为统一目录改造上游构建结构。

## 检查输出

模块和检查项使用简短、稳定的小写名称，词间用连字符，例如：

```text
build/checks/gslc/telemetry/
build/checks/gslc/surface-map/
build/checks/gslc/public-controller/
build/checks/ftb/shared-team/
```

新增模块沿用 `build/checks/<模块>/<检查项>/`，不使用 `new`、`test2`、`after-cleanup` 等临时名称，也不默认累积带时间戳的目录。脚本按自身位置定位仓库，默认输出不随启动工作目录变化。

默认只保留每类检查最近一次输出。GSLC 检查在依赖验证通过后清理自己的固定输出目录再运行，失败日志留在该目录；依赖缺失时保留上次结果。FTB 公共团队检查重新编译时清理自己的输出目录，每次运行前清理该目录中的旧运行日志。不要并发运行同一个检查，避免共享输出互相覆盖。

现有 GSLC 脚本兼容显式传入运行环境、候选 JAR 和输出目录。自定义输出目录不自动清空，避免删除调用者的其他文件。输出不得混入源码、固定依赖或正式实例。

## 当前入口

先配置 JDK 8，再从仓库根目录执行：

```sh
python3 tools/build.py
python3 GalaxySpace/tests/telemetry_dimension/run_probe.py
python3 GalaxySpace/tests/telemetry_dimension/run_surface_probe.py
python3 GalaxySpace/tests/public_controller/run_probe.py
```

后三项默认读取 `.local/probe-runtime/`，候选包按 `version.txt` 从 `build/libs/GSLaunchCompat-<版本>.jar` 取用。本机环境需自行配置，不将绝对路径写入已跟踪脚本。兼容调用：

```text
python3 <检查脚本> [运行环境目录 [候选JAR [自定义输出目录]]]
```

FTB 公共团队检查沿用 [FTB 开发说明](../FTB-Quests/DEVELOPMENT.md#公共团队隔离检查)中的 Gradle 命令，编译输出和运行日志统一到 `build/checks/ftb/shared-team/`；检查结果同时打印到终端。纯临时的测试世界继续使用系统临时目录。

## 固定材料和清理

`dev-tools/` 中每项固定材料都需在目录说明中登记用途、来源或维护入口。文件名中的版本是该材料版本，不代表最终生成包的版本；不要把必需底包误当旧输出删除。

`build/` 可由对应构建或检查重新生成，但清理后需先重建最终模组包再进行导出。`.local/` 与 `server/` 可能包含不可再生成的本机配置和运行数据，不作为构建缓存清理。

不新增职责不明的状态目录。确需持久状态时按用途放入 `.local/` 或所属运行实例，并在对应说明中登记。
